# Contrato de integração — entregas e financeiro v2

Base: main e3ab7ef. Projeto existente, frontend estático Cloudflare Pages, backend Supabase Postgres/Edge Functions. Não inicializar projeto WebDev nem alterar hospedagem. WebDev LSP retornou `No active project`; usar Node syntax/VM, TypeScript local e PostgreSQL PGlite como verificações. Não fazer deploy, push, pagamentos nem modificar contas a partir de subtarefas.

## Objetivo e decisões

Implementar a proposta original em `/home/ubuntu/antifraude-runtime/proposta-original.txt`: taxa nominal 7% dos produtos em entregas (5% plataforma + 2% motoboy), aceite atômico, coleta/em entrega, remuneração/histórico, confiabilidade sem acusação automática, ofertas aos motoboys autorizados/disponíveis, rede multicomércio, cancelamentos categorizados, cancelamento do comprador só antes do aceite, atribuição dentro de catalogo-admin e oferta automática ao marcar pronto, remover atribuição de entregadores-admin.

Decisões financeiras pendentes do usuário: só Pix vs também presencial; retirada/consumo 5% vs 7%. **Não ativar a nova política em produção enquanto estiverem pendentes.** Implementar configuração `catalogo_fluxo_config` singleton `id=true, ativo=false, somente_pix=false, taxa_sem_entrega_percentual=5`. Taxas de entrega 5+2, retirada padrão 5 sem remuneração; se usuário pedir 7 sem entregador, exige destino dos 2 antes de ativar. Pedidos antigos permanecem com versão 1, taxas e regras financeiras pactuadas; não aumentar cobranças retroativamente.

Motoboy tem valor a receber após código correto; `paga` somente após repasse real comprovado pelo administrador. Não automatizar transferência bancária/MP. Split 1:1 Mercado Pago não significa split automático de três recebedores: plataforma recebe sua retenção + reserva logística e contabiliza separadamente os 2%. Quando houver presencial, manter financiamento pendente até a comissão correspondente realmente recebida. Incentivo/índice não prova ausência de conluio.

## Campos e estados

Adicionar a `catalogo_pedidos`: `versao_financeira smallint default 1`, `taxa_motoboy_centavos int default 0`, `taxa_total_centavos int` (backfill taxa_plataforma nos legados), `aceito_em timestamptz`, `entrega_status text` (nao_atribuido/ofertado/reservado/coletado/em_entrega/entregue/cancelamento_solicitado/cancelado), `motoboy_preferido_id uuid`, `modo_distribuicao text` (rede/direto), `coletado_em`, `em_entrega_em`, `codigo_entrega_enc text`, `reembolso_pendente boolean default false`. Não remover colunas nem estados originais. `taxa_plataforma_centavos` conserva parcela 5%; taxa_total soma parcelas arredondadas separadamente em centavos. Repasse bruto = subtotal - taxa_total + entrega, sem confundir tarifa MP/taxa de entrega.

Tabelas privadas RLS + REVOKE PUBLIC/anon/authenticated + acesso service_role: perfil motoboy/disponibilidade/chave Pix opcional, remunerações (uma por pedido e beneficiário fixo), lançamentos financeiros v2, ocorrências/cancelamentos categorizados, repasses auditados. Sem exposição de tokens/códigos/hashes/chaves Pix do entregador em listagens do comércio ou ofertas.

Status físico e financeiro separados. `status_pagamento=aprovado` só por provedor/baixa presencial válida; cancelamento do transporte não simula estorno. Webhook não rebobina preparo/coleta/entrega. Nenhum timeout marca entrega/pagamento como concluído.

## RPCs públicas de backend (EXECUTE só service_role, SECURITY DEFINER search_path='')

Todas retornam `{ok:true,...}` ou `{ok:false,http_status,mensagem}`. IDs de operador vêm exclusivamente do JWT validado pela Edge Function; nunca aceitar ID enviado no body como identidade. Admin plataforma: UUID já existente `4b9a0233-6b72-4573-aebd-d596c5b15e1b`.

1. `catalogo_fluxo_precificar(p_modalidade text,p_subtotal_centavos int)`: retorna `versao_financeira,taxa_plataforma_centavos,taxa_motoboy_centavos,taxa_total_centavos,somente_pix,ativo`. Config desligada retorna v1/5/0. Snapshot é imutável por pedido.
2. `catalogo_operar_pedido_v2(p_operador_id uuid,p_comercio_id text,p_pedido_id uuid,p_acao text,p_motoboy_id uuid default null,p_motivo text default null)`: ações `aceitar`, `pronto`, `atribuir`, `solicitar_cancelamento`, `rejeitar_antes_aceite`. Proprietário exato/admin; trava pedido FOR UPDATE. Aceitar Pix exige pagamento aprovado. V2 presencial, se permitido, registra parcela plataforma no aceite, evitando depender do código; cancelamento depois do aceite cria ocorrência, não elimina comissão. Pronto oferta à rede autorizada/disponível salvo preferência de motoboy definida antes; atribuir não equivale ao aceite pelo motoboy. Não permitir reatribuir após coleta. Antes do aceite cancelamento/rejeição pode encerrar transporte, mantendo reembolso pendente se Pix aprovado.
3. `catalogo_listar_entregas_v2(p_operador_id uuid,p_offset int default 0)`: `{pedidos,has_more}`; ofertas só prontas, usuário disponível/apto/com vínculo ativo; ofertas não têm nome/telefone/endereço/observações do comprador. Campos seguros: pedido_id,comercio_id,comercio_nome,status,entrega_status,oferta,total_centavos,taxa_motoboy_centavos,criado_em. PII só para responsável que aceitou. Atribuídos incluem campos antigos e forma_pagamento/status_pagamento, itens seguros. Usuário não pode enviar comercio_id para elevar privilégios.
4. `catalogo_motoboy_acao_v2(p_operador_id uuid,p_acao text,p_pedido_id uuid default null,p_disponivel boolean default null,p_motivo text default null,p_categoria text default null,p_chave_pix text default null)`: ações `disponibilidade`, `aceitar_entrega`, `coletar`, `em_entrega`, `desistir`, `registrar_ocorrencia`, `salvar_chave_pix`. Aceite primeiro vence sob trava; revalida vínculo, disponibilidade, análise, preferência e fase. Coleta/em entrega só responsável. Desistência antes coleta reoferta/audita; depois coleta vira ocorrência e não solta pedido nem apaga cobrança.
5. `catalogo_motoboy_extrato_v2(p_operador_id uuid,p_offset int default 0)`: `{saldo:{a_receber_centavos,pago_centavos,retido_centavos},confiabilidade:{indice,situacao,amostra,concluidas,cancelamentos_pre_coleta,cancelamentos_pos_coleta,ocorrencias},entregas_concluidas:[],pagamentos:[],perfil:{disponivel,chave_pix}}`. Somente própria conta. Escore sem amostra suficiente é null/em formação; cancelamento do comprador/comércio não é automaticamente culpa do motoboy. Alegação não é ocorrência comprovada. Análise preventiva não é banimento/culpa e precisa revisão/reversão do admin.
6. `catalogo_cancelar_comprador_v2(p_pedido_id uuid,p_status_token_hash text,p_motivo text default null)`: hash de token 256-bit próprio pedido; trava pedido; recusa depois aceito_em/preparo com mensagem solicitada no anexo. Cancelamento em duas etapas na UI + guarda real no backend. Nunca ID da loja isolado, nem token público legado, nem owner fallback autorizam cancelar como comprador.
7. Preservar assinaturas `catalogo_confirmar_entrega_motoboy`, `catalogo_confirmar_entrega_autenticada` e wrapper/base já existente. Version1 mantém caminho antigo. V2 entrega exige responsável ativo/atribuído + coleta/em entrega + código válido/expiração/tentativas; dono não cria crédito ao fingir-se motoboy. V2 retirada não gera bônus. Confirmação cria remuneração UMA vez e mantém a comissão plataforma já registrada no aceite/pagamento. Retida se financiamento pendente/divergente; a_receber se taxa comprovadamente recebida.
8. `catalogo_aplicar_pagamento_v2(p_pedido_id uuid,p_status text,p_valor_centavos int,p_taxa_centavos int,p_referencia text)`: estado de pagamento obtido diretamente do MP pela Edge Function (não browser). Só approved/aprovado com valor exato; taxa pode null => revisão financeira/sem saldo disponível se não comprovada. Pedido e ledger travados/idempotentes; status físicos avançados não retrocedem. Refunded/estornado/charged_back congelam/estornam créditos NÃO pagos; se já pagos cria pendência para revisão, não dinheiro fictício. Preservar operações legacy.
9. `catalogo_operacao_admin_v2(p_operador_id uuid,p_acao text,p_ocorrencia_id uuid default null,p_decisao text default null,p_motivo text default null,p_motoboy_id uuid default null,p_pedido_ids uuid[] default null,p_referencia text default null,p_comprovante text default null)`: admin apenas; `listar_operacao` retorna ocorrencias e remunerações disponíveis/beneficiário/chavePix, `resolver_ocorrencia` com revisão fundamentada (cancelamento legitimo/manter/ocorrência comprovada), `registrar_repasse` exige prova/referência e somente créditos disponíveis não pagos, trava todos, marca repasse registrado sem executar transferência. Admin review nunca declara reembolso MP real efetuado nem dinheiro entregue que não tenha prova.
10. Função `catalogo_reavaliar_confiabilidade_v2`/job nativo opcional: apenas sinaliza histórico e atraso comprováveis; sem enviar dinheiro, concluir entrega ou banir por número público arbitrário. Inserções de ocorrências únicas/idempotentes. Monitor, se criado, flags desligadas até validação.

## APIs e respostas de frontend

`catalogo-entregas`: mantém ações antigas de gestão de vínculos. Novas: `listar_entregas` usa RPC v2; `aceitar_entrega`, `coletar`, `em_entrega`, `desistir_entrega`, `registrar_ocorrencia`, `definir_disponibilidade`, `salvar_chave_pix`, `consultar_extrato`. `confirmar_entrega` usa wrapper existente; devolver success/pedido. Gestão `atribuir_pedido` usa operar_v2; body comercio_id,pedido_id,motoboy_id null=rede. `operacao_admin`, `resolver_ocorrencia`, `registrar_repasse` só admin RPC. Frontend nunca envia valor do bônus, saldo ou identidade do beneficiário da entrega para decidir crédito.

`catalogo-pedidos-offline-admin`: manter fechamento/faturas, listar agora ambos provedores com campos v2 e `motoboy_id` quando atribuído; `atualizar_status` mapeia em_preparo→aceitar, pronto→pronto, cancelado→solicitar_cancelamento (recusa definitiva pós aceite substituída por ocorrência). Confirmação wrapper existente compatível.

`catalogo-pedido-offline`: consultar_status para offline e Pix com token forte; devolve status,status_pagamento,aceito_em,codigo_ativo,concluido,reembolso_pendente; código só ao comprador com token forte se necessário, não ao comércio/admin. `cancelar_pedido` verifica token+hash e RPC; nunca ativa cancelar por prova fraca. Criar offline precifica e valida somente_pix (quando ativo); snapshotv2/hash token/código. Pix também cria comprovante de entrega, status_token e código com hash. Endpoint público não permite confirmação/baixa.

Pagamento MP: split documentado usa Payments API `/v1/payments` e `application_fee`, seller OAuth. Para v2 usar esse modelo, conservar compatibilidade de pedidos Orders API antigos na webhook. Assinatura webhook admite timestamps segundos/milissegundos e comparação constante; valida referências, collector, montante/currency, taxa, estado diretamente via GET API. Guardar payment_id/order_id conforme provedor real. Metadados incluem versão, modelo API, taxa snapshot; tokens nunca retornados à gestão. Nada de destruir rastros se MP já criou pagamento e houve falha local; recuperação idempotente.

## Interfaces obrigatórias

- Owner: lista de pedidos mantém produtos/fatura/confirm dialog, atribuição seletor e opção Motoboys disponíveis na própria linha, pronto reoferta automático, cancelar após aceite vira solicitação com motivo. Remover inteiramente seção atribuição em entregadores-admin, mantendo cadastro/suspensão. Página admin operacional separada com auth forte para revisão e repasses manuais comprovados.
- Motoboy: disponibilidade opt-in, ofertas/aceitar, minhas entregas com coletar/em entrega/código, ganhos/acumulado/histórico e confiabilidade com texto prudente, chave Pix própria opcional. Só vínculos autorizados, sem catálogo/faturas. Manter proteção contra resposta antiga de outra sessão, limpeza logout/pagehide, escaping e URLs seguras.
- Buyer: cancelar ao lado ver código, duas etapas; depois aceite mensagem exata do anexo + contato WhatsApp; não reintroduzir Remover deste dispositivo; código só disponível quando adequado, some após entrega; preservar prova/estado necessário para cancelamento/reembolso, tratar Pix pago e cancelado separadamente. Não criar pedidos reais em testes.
